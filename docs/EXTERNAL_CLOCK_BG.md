# Подготвен външен часовник за Matchpulse

Статус: чака еднократна външна връзка и разрешение за задействане.
Това е предложение за настройка, а не активирана задача. JSON файлът е
общ HTTP шаблон, не готов API import за cron-job.org.
GitHub остава мястото за изтегляне, проверки, архивиране и публикуване.
Външната услуга само изпраща заявка за стартиране.

## Точни настройки

- Услуга: cron-job.org, безплатна, с потребителски HTTP заявки.
- Име: Matchpulse — проверка на данните.
- Часова зона: Europe/Sofia.
- График: на 13-а и 43-а минута всеки час (`13,43 * * * *`).
- Метод: POST.
- URL: `https://api.github.com/repos/planenp993/matchpulse-auto/actions/workflows/refresh-clock.yml/dispatches`
- Headers: `Accept: application/vnd.github+json`, `Content-Type: application/json`,
  `Authorization: Bearer <ограничения GitHub токен>`.
- Body:

```json
{"ref":"main","inputs":{"mode":"auto"}}
```

Ограничен fine-grained GitHub token: само хранилището
`planenp993/matchpulse-auto`, само Actions → Read and write (Metadata read е
автоматично), с крайна дата на валидност. Actions write позволява управление
на Actions в това хранилище; не е ограничение само до един workflow.
Реалният токен се въвежда лично в Header полето на външната услуга;
в GitHub/публичния шаблон остава само заместителят. Създаването на акаунт,
издаването на токена и предоставянето му на cron-job.org изискват еднократно
решение/действие на собственика. Токенът не се изпраща като съобщение в чата.

Без съгласие за новата външна услуга и предоставяне на тези права настройката
остава неактивна. При отказ услугата се изключва и token-ът се отнема в GitHub.

## Какво ще се изпълнява

Заявката стартира `refresh-clock.yml` в режим auto. Той чете текущите източникови
часовници и при дължима работа извиква същия проверен `update.yml`.
Изтеглянето от Statarea запазва около 30 минути между опитите; бавните източници
имат отделни интервали. Общите concurrency групи и повторното планиране пазят
от двойно изтегляне при близки вътрешно/външно задействани проверки.
Моделите, писателите и старите дневникови редове остават същите.

## Как се доказва автоматиката

1. Тестовата заявка трябва да върне HTTP 204, после GitHub run да е успешен.
2. Изчаква се истинско планирано изпълнение от външната услуга — не бутона Test.
3. Неговият час се сверява с новия GitHub run и успешния Statarea receipt.
4. `last_statarea_success_trigger.run_id` трябва да сочи съответния GitHub run.

GitHub събитието при външен HTTP часовник ще бъде `workflow_dispatch`.
Автоматичното задействане се доказва от планираната история на външната услуга,
свързана с GitHub run; не се представя като native `schedule`.

Източници за настройките: https://cron-job.org/en/faq/ и
https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event
