## Какво ще се изпълнява

Заявката стартира `refresh-clock.yml` в режим auto. Той чете текущите източникови
часовници и при дължима работа извиква същия проверен `update.yml`.
Изтеглянето от Soccerway запазва около 30 минути между опитите; бавните източници
имат отделни интервали. Общите concurrency групи и повторното планиране пазят
от двойно изтегляне при близки вътрешно/външно задействани проверки.
Моделите, писателите и старите дневникови редове остават същите.

## Как се доказва автоматиката

1. Тестовата заявка трябва да върне успешен HTTP 200 (новият GitHub API;
   response съдържа run ID/URL) или 204 при по-стара версия. После самият
   GitHub run трябва да завърши успешно. Запазва се отговорът за сверяване.
2. Изчаква се истинско планирано изпълнение от външната услуга — не бутона Test.
3. Неговият час се сверява с новия GitHub run и успешния Soccerway receipt.
4. `last_soccerway_success_trigger.run_id` трябва да сочи съответния GitHub run.

GitHub събитието при външен HTTP часовник ще бъде `workflow_dispatch`.
Автоматичното задействане се доказва от планираната история на външната услуга,
свързана с GitHub run; не се представя като native `schedule`.
